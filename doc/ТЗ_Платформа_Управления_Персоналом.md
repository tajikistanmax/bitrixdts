## 1. Цель и назначение системы

**Цель:** создать корпоративную платформу для управления персоналом, задачами, проектами, документооборотом и внутренними коммуникациями, способную работать как в облаке, так и в локальной сети предприятия (on-premise).

**Основные задачи:**
- Учёт сотрудников и организационной структуры.
- Постановка и контроль задач/проектов (поручений).
- Учёт рабочего времени, посещаемости, отпусков, командировок.
- Внутренний документооборот с согласованиями.
- Коммуникации: чат, видеосовещания, уведомления.
- KPI, отчёты, контроль исполнительской дисциплины.

**Ключевая особенность:** гибридный режим работы — система функционирует офлайн в локальной сети и синхронизируется с облаком при наличии связи (offline-first).

## 2. Анализ аналогов

| Система | Сильные стороны | Что берём в проект |
|---------|-----------------|--------------------|
| **Bitrix24** | Всё в одном: CRM, задачи, чат, документы, оргструктура | Модель «единый портал», лента новостей, оргструктура |
| **Microsoft Teams** | Чат, видеозвонки, интеграции | Коммуникации, видеоконференции |
| **Asana** | Удобные задачи, представления (список/доска/таймлайн) | Гибкие представления задач |
| **Monday.com** | Визуальные доски, кастомные поля | Кастомизация сущностей, цветовые статусы |
| **Jira Software** | Сложные workflow, agile-доски, спринты | Workflow-движок, статусные переходы |
| **ClickUp** | Иерархия (пространства→папки→списки→задачи) | Иерархическая структура проектов |
| **Odoo** | Модульность, HR, посещаемость, табель, отпуска | Модульная архитектура, HR-модули |

**Вывод по архитектуре:** берём модульную монолитную архитектуру (modular monolith) с возможностью выделения сервисов, как в Odoo, + гибкий workflow-движок (Jira) + единый портал (Bitrix24).

## 4. Функциональные требования (модули)

### 4.1. Модуль «Сотрудники»
- CRUD сотрудников (ФИО, контакты, фото, должность, подразделение).
- Карточка сотрудника:
  - ФИО
  - **ИНН** (обязательное поле для РФ)
  - Должность
  - Подразделение
  - Телефон, Email
  - Дата приёма на работу
  - Статус сотрудника
  - Фотография
  - **История изменений** (аудит всех полей)
- Статусы: работает / в отпуске / уволен / командировка / на больничном.
- Импорт/экспорт (CSV, Excel).
- Привязка к учётной записи (логин, роль).
- Поиск и фильтрация сотрудников (по ФИО, ИНН, должности, подразделению).

### 4.2. Модуль «Организационная структура»
- Дерево подразделений с фиксированными уровнями:
  - **Центральный аппарат**
  - **Управления**
  - **Отделы**
  - **Секторы**
- Неограниченная вложенность внутри уровней.
- Должности и связи «руководитель → подчинённый».
- Визуальная схема оргструктуры (дерево + граф).
- Делегирование прав руководителя.

### 4.3. Модуль «Задачи»
- Создание задач:
  - Название задачи
  - Описание
  - **Исполнитель** (ответственный)
  - **Соисполнители** (несколько человек)
  - **Контролёр** (отдельная роль для контроля)
  - Приоритет (низкий/средний/высокий/критический)
  - Дата начала
  - Срок исполнения
  - Файлы и документы
- Статусы задач (строгий workflow):
  - **Новая**
  - **В работе**
  - **На согласовании**
  - **Выполнена**
  - **Отклонена**
  - **Просрочена** (авто-переход при истлении срока)
- Контроль исполнения:
  - Автоматические уведомления
  - Напоминания о сроках
  - Контроль просрочек
  - История действий (кто, что, когда изменил)
- Представления: список, канбан-доска, календарь, диаграмма Ганта.
- Комментарии, упоминания (@mention).
- Повторяющиеся задачи (расписание).
- Зависимости между задачами.
- Учёт затраченного времени (таймер).

### 4.4. Модуль «Проекты»
- Создание проекта:
  - Название, описание
  - **Руководитель проекта**
  - Участники проекта и роли
  - Этапы проекта
  - Процент выполнения (авто-расчёт от задач)
- Отчёты по проекту.
- Канбан-доска с колонками:
  - **Новые**
  - **В работе**
  - **На проверке**
  - **Выполненные**
- Иерархия: Пространство → Проект → Группа задач → Задача.
- Сроки, бюджет.
- Шаблоны проектов.
- Таймлайн, отчёты по проекту.

### 4.5. Модуль «Посещаемость»
- Отметки прихода/ухода (вручную, по терминалу, по геолокации/IP).
- Интеграция с биометрией/турникетами (опционально, через API).
- Журнал посещаемости, опоздания, переработки.

### 4.6. Модуль «Табель»
- Автоформирование табеля на основе посещаемости.
- Учёт типов времени: явка, отпуск, больничный, командировка, прогул.
- Утверждение табеля руководителем.
- Экспорт в формате Т-13 (РФ) / настраиваемые шаблоны.

### 4.7. Модуль «Отпуска»
- Заявки на отпуск (виды: ежегодный, без содержания, учебный).
- График отпусков.
- Маршрут согласования (руководитель → HR).
- Остаток дней отпуска, баланс.

### 4.8. Модуль «Командировки»
- Заявки на командировку:
  - Цель, направление (маршрут)
  - Даты (сроки)
  - Бюджет
- Согласование (руководитель → HR → бухгалтерия).
- Авансовый отчёт.
- **Отчёт о командировке** по завершении.
- Привязка к табелю.

### 4.9. Модуль «Документооборот»
- Типы документов:
  - **Входящие документы** (регистрация, присвоение номера, назначение исполнителя, контроль исполнения)
  - **Исходящие документы** (подготовка, согласование, подписание, отправка)
  - **Внутренние документы**:
    - Приказы
    - Распоряжения
    - Служебные записки
    - Письма
- Согласование документов (workflow):
  - Этапы: Подготовка → Согласование → Подписание → Архивирование
  - Маршруты согласования (последовательные/параллельные)
- **Электронная цифровая подпись (ЭЦП)**:
  - Интеграция с ЭЦП (КриптоПро, Минцифры)
  - Подписание документов
  - Проверка подписей
- Архив документов:
  - Хранилище (папки, версии, права доступа)
  - Поиск, фильтрация
  - История изменений
  - Скачивание
- Шаблоны документов, генерация из шаблона.
- Журнал входящих/исходящих.

### 4.10. Модуль «Чат»
- Личные сообщения (1-on-1).
- Групповые чаты.
- Каналы (новостные, тематические).
- Передача файлов.
- Реакции, упоминания.
- История переписки, поиск.
- Уведомления (push, email).

### 4.11. Модуль «Видеосовещания»
- Создание/планирование встреч.
- Приглашение участников (по email, из оргструктуры).
- Видео/аудио, демонстрация экрана.
- **Запись совещания** (опционально).
- Технология: WebRTC (медиасервер mediasoup / Janus / LiveKit).

### 4.12. Модуль «KPI»
- Настройка показателей (цель, факт, вес, период).
- Привязка к сотрудникам/отделам.
- Автоматический расчёт по данным задач/посещаемости/продаж.
- Показатели эффективности:
  - Количество выполненных задач
  - Количество просроченных задач
  - Средний срок исполнения
  - Активность сотрудника
- **Рейтинг сотрудников**:
  - По подразделению
  - По организации
  - По периоду
- Дашборды и динамика.

### 4.12.1. Контроль поручений
- Постановка поручения (отдельный тип задачи с жёстким контролем).
- Назначение ответственных.
- Контроль сроков.
- Автоматические напоминания.
- Отчёты по исполнению поручений.

### 4.13. Модуль «Отчёты»
- Конструктор отчётов (фильтры, группировки, графики).
- Готовые отчёты:
  - **Отчёт по сотрудникам**
  - **Отчёт по задачам**
  - **Отчёт по посещаемости**
  - **Отчёт по отпускам**
  - **Отчёт по командировкам**
  - **Отчёт по документообороту**
  - **KPI-отчёты**
  - Отчёт по исполнительской дисциплине
  - Загруженность сотрудников
  - Просроченные задачи
  - KPI подразделений
- Экспорт: PDF, Excel, CSV.
- Расписание автоотправки отчётов.
- Аналитические панели **Dashboard** «Управление персоналом и поручениями».

### 4.14. Сквозные модули
- **Лента активности** (новости портала).
- **Новости организации**:
  - Публикация новостей
  - Комментарии
  - Категории новостей
- **Объявления**:
  - Публикация объявлений
  - Прикрепление файлов
  - Ограничение по подразделениям
- **Уведомления**:
  - Системные уведомления
  - Email-уведомления
  - Push-уведомления
- **Календарь** (личный, командный, переговорные).
- **Поиск** (глобальный по всем сущностям).
- **Настройки** (организация, права, интеграции).
- **Автоматизация** (low-code / no-code):
  - Легко настроить без программирования
  - Триггеры и действия (если X → выполни Y)
  - Автоматизация рутинных процессов (напоминания, уведомления, переназначение задач)

### 4.15. ИИ и BitrixGPT (опционально)

- Автозаполнение полей

## 5. Роли и права доступа (RBAC)

| Роль | Описание | Основные права |
|------|----------|----------------|
| **Суперадмин** | Владелец платформы (вендор) | Управление всеми организациями, лицензиями |
| **Администратор** | Полный доступ ко всем функциям организации | Все модули в рамках своей организации |
| **Руководитель** | Управление подразделением, задачами и отчетами | Задачи, KPI, согласования, отчёты по отделу, утверждение табеля/отпусков |
| **Сотрудник** | Рядовой пользователь | Свои задачи, чат, заявки, документы, личное время |
| **Контролер** | Контроль исполнения поручений и формирование отчетов | Просмотр всех задач, контроль сроков, формирование отчётов по поручениям |
| **HR-менеджер** | Кадровый учёт | Сотрудники, табель, отпуска, командировки, больничные |
| **Наблюдатель/Гость** | Ограниченный доступ | Просмотр определённых сущностей |

**Модель прав:** RBAC + ABAC (атрибутивная) на уровне записей.
Права проверяются по схеме: `роль` → `разрешение` → `ресурс` → `область видимости (своё / отдел / организация)`.

## 6. Нефункциональные требования

| Категория | Требование |
|-----------|------------|
| **Производительность** | API-ответ < 200 мс (P95) при 1000 одновременных пользователей |
| **Масштабируемость** | Горизонтальное масштабирование backend, репликация БД |
| **Доступность** | 99.5% (облако), офлайн-режим в локальной сети |
| **Мультиарендность** | Изоляция данных по `organization_id` (tenant) |
| **Локализация** | RU/EN, мультиязычность интерфейса, часовые пояса |
| **Совместимость** | Браузеры: Chrome, Edge, Firefox, Safari (последние 2 версии) |
| **Мобильность** | Адаптивный web + мобильное приложение (PWA / React Native) |
| **Резервное копирование** | Ежедневный бэкап БД, point-in-time recovery |
| **Логирование/аудит** | Полный аудит действий пользователей |

## 7. Архитектура системы

### 7.1. Общая схема (гибридная)

```
┌──────────────────────────────────────────────────────────────────────┐
│                       ОБЛАКО / ЦЕНТРАЛЬНЫЙ VPS                          │
│  ┌──────────────────────────────────────────────────────────────────┐ │
│  │  API Gateway (Nginx) → Backend (Node.js, modular monolith)        │ │
│  │  ├─ Auth Service        ├─ HR Service       ├─ Tasks Service       │ │
│  │  ├─ Docs Service        ├─ Chat Service      ├─ KPI/Reports        │ │
│  │  ├─ Sync Service (синхронизация с узлами)                          │ │
│  │  PostgreSQL (master) │ Redis │ S3/MinIO (файлы) │ WebRTC SFU       │ │
│  └──────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────┘
                    ▲                         ▲
       HTTPS/WSS    │                         │   HTTPS/WSS
        синхронизация│                         │
        ┌────────────┴───────────┐ ┌───────────┴────────────┐
        │   ЛОКАЛЬНЫЙ УЗЕЛ (офис) │ │  ЛОКАЛЬНЫЙ УЗЕЛ (филиал)│
        │  Node.js + PostgreSQL   │ │  Node.js + PostgreSQL   │
        │  (offline-first)        │ │  (offline-first)        │
        │  ├ Web-клиенты (LAN)    │ │  ├ Web-клиенты (LAN)    │
        │  └ Sync Agent           │ │  └ Sync Agent           │
        └─────────────────────────┘ └─────────────────────────┘
```

### 7.2. Стиль архитектуры
- **Modular Monolith** на старте (быстрее разрабатывать, проще деплой).
- Чёткие границы модулей → возможность выделить в микросервисы позже.
- Разделение слоёв: `Routes → Controllers → Services → Repositories → DB`.
- Event-driven внутри (шина событий) для слабой связанности модулей.

### 7.3. Структура backend-проекта
```
backend/
├── src/
│   ├── modules/
│   │   ├── auth/            # аутентификация, токены
│   │   ├── employees/       # сотрудники
│   │   ├── org-structure/   # оргструктура
│   │   ├── tasks/           # задачи
│   │   ├── projects/        # проекты
│   │   ├── attendance/      # посещаемость
│   │   ├── timesheet/       # табель
│   │   ├── vacations/       # отпуска
│   │   ├── trips/           # командировки
│   │   ├── documents/       # документооборот
│   │   ├── chat/            # чат
│   │   ├── meetings/        # видеосовещания
│   │   ├── kpi/             # KPI
│   │   ├── reports/         # отчёты
│   │   └── sync/            # синхронизация офлайн/онлайн
│   ├── core/                # общие утилиты, middleware, ошибки
│   ├── db/                  # миграции, подключение, репозитории
│   ├── events/              # шина событий
│   └── server.js
├── migrations/              # SQL-миграции
└── tests/
```

Каждый модуль: `module.routes.js` → `module.controller.js` → `module.service.js` → `module.repository.js`.

## 8. Технологический стек

> Стек выбран с учётом текущего опыта проекта (Node.js + Express + PostgreSQL + React/Vite).

| Слой | Технология | Обоснование |
|------|------------|-------------|
| **Backend** | Node.js 20 LTS + Express (или NestJS) | Единый язык с фронтом, экосистема, ваш опыт |
| **Язык backend** | TypeScript | Типобезопасность, меньше багов |
| **База данных** | PostgreSQL 15+ | ACID, JSONB, репликация, ваш текущий стек |
| **ORM/Query** | Prisma или Knex + миграции | Типизация, удобные миграции |
| **Кэш / Pub-Sub** | Redis | Сессии, очереди, real-time события |

## 11. Режим онлайн/офлайн и синхронизация

### Принцип Offline-first
- Локальный узел (Node.js + PostgreSQL) в сети предприятия работает автономно.
- Клиенты в LAN подключаются к локальному узлу → нет зависимости от интернета.
- Sync Agent синхронизирует локальную БД с облаком при наличии связи.

### Механизм синхронизации
1. Каждая запись имеет `sync_version` (монотонный счётчик) и `updated_at`.
2. **Push:** узел отправляет «грязные» записи (`is_dirty`) в облако.
3. **Pull:** узел запрашивает изменения из облака `since = last_version`.
4. **Разрешение конфликтов:**
   - По умолчанию **Last-Write-Wins** (по `updated_at` + приоритет источника).
   - Для критичных сущностей (табель, документы) — ручное разрешение/блокировка.
5. **Дельта-синхронизация:** передаются только изменения, не вся база.
6. Все операции идемпотентны (по `entity_id` + `sync_version`).

```
┌────────────┐   push (delta)   ┌────────────┐
│ Локальный   │ ───────────────► │  Облако     │
│ узел (LAN)  │ ◄─────────────── │  (master)   │
└────────────┘   pull (delta)    └────────────┘
   работает офлайн           синхронизация при связи
```

### Клиент (web/PWA)
- Service Worker + IndexedDB для офлайн-кэша.
- Очередь действий при отсутствии связи → отправка при восстановлении.

## 12. Развёртывание (локально / VPS / облако)

### Вариант A: Только локально (один офис)
```
docker-compose up -d
# Поднимает: postgres, redis, backend, frontend(nginx), minio
```
- Установщик для Windows (по аналогии с вашим `market-local`): обёртка над docker-compose или portable-сборка с автозапуском.

### Вариант B: Гибрид (офис + облако)
- Облако: центральный сервер (VPS) с master-БД.
- Каждый офис: локальный узел + Sync Agent (указывает `cloud_url`, `node_id`).
- Регистрация узла в облаке при первом запуске.

### Вариант C: Полностью облако (SaaS)
- Мультиарендность по `organization_id`.
- Масштабирование backend за балансировщиком, реплики PostgreSQL.

**docker-compose (эскиз):**
```yaml
services:
  postgres:   { image: postgres:15, volumes: [pgdata:/var/lib/postgresql/data] }
  redis:      { image: redis:7 }
  minio:      { image: minio/minio, command: server /data }
  backend:    { build: ./backend, depends_on: [postgres, redis, minio] }
  frontend:   { build: ./frontend, ports: ["80:80"] }
volumes: { pgdata: {} }
```
